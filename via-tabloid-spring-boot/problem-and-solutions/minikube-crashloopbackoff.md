# CrashLoopBackOff: via-tabloid-spring-boot on Minikube

## What is CrashLoopBackOff?

`Back-off restarting failed container` (also shown as `CrashLoopBackOff` in `kubectl get pods`) means Kubernetes started the container, the container crashed, and Kubernetes keeps restarting it. Each restart waits longer than the previous one (1s → 2s → 4s → 8s → … up to 5 minutes). The container is stuck in a crash loop.

---

## Problem 1: `ErrImageNeverPull` — image not found in Minikube

### Symptom
```
Container image "via-tabloid-spring-boot:latest" is not present with pull policy of Never
Error: ErrImageNeverPull
```

### Root Cause
Minikube runs its own isolated Docker daemon, separate from the host machine's Docker.
When you build an image on the host (`docker build ...`), it is stored in the host's Docker — **not** inside Minikube. The deployment uses `imagePullPolicy: Never`, which tells Kubernetes to never pull from a registry and only use what is already present locally inside Minikube. Since the image doesn't exist there, the pod fails immediately.

### Solution
Load the image into Minikube's Docker daemon:
```bash
# Option A: load from a saved .tar file
minikube image load via-tabloid-spring-boot:latest

# Option B: build directly inside Minikube's daemon (current terminal session only)
eval $(minikube docker-env)
docker build -t via-tabloid-spring-boot:latest .
```

## Problem 2: `secret "via-tabloid-secrets" not found`

### Symptom
```
Error: secret "via-tabloid-secrets" not found
```

### Root Cause
The secret is defined as a `secretGenerator` in `kustomization.yaml`, which means it is generated by **Kustomize** from the `k8s/.env` file at apply time. Running `kubectl apply -f k8s/` applies individual YAML files and **ignores `kustomization.yaml`** entirely — so the secret is never created.

### Solution
Use `-k` (kustomize mode) instead of `-f`:
```bash
kubectl apply -k k8s/
```

## Problem 3: `FATAL: database "via_tabloid" does not exist` — CrashLoopBackOff

### Symptom
```
FATAL: database "via_tabloid" does not exist
org.hibernate.exception.GenericJDBCException: Unable to obtain isolated JDBC connection
```
Pod status: `CrashLoopBackOff`

### Root Cause
Two bugs in `k8s/postgres-deployment.yaml`:

**Bug 1 — Database name mismatch:**
- `POSTGRES_DB: via-tabloid` (hyphen) → Postgres creates a database named `via-tabloid`
- `DB_URL_DOCKER=jdbc:postgresql://postgres:5432/via_tabloid` (underscore) → Spring Boot connects to `via_tabloid`
- These two names never match, so the database the app expects simply does not exist.

**Bug 2 — Wrong init script directory:**
- Init script was mounted at `/docker-entrypoint-initdb/init.sql`
- Postgres only auto-executes scripts inside `/docker-entrypoint-initdb.d/` (note the `.d` suffix)
- The init SQL was silently ignored, so tables were never pre-created.

### Solution

**Fix 1** — Align the database name in `k8s/postgres-deployment.yaml`:
```yaml
# Before
- name: POSTGRES_DB
  value: via-tabloid

# After
- name: POSTGRES_DB
  value: via_tabloid
```

**Fix 2** — Correct the init script mount path in `k8s/postgres-deployment.yaml`:
```yaml
# Before
volumeMounts:
  - mountPath: /docker-entrypoint-initdb/init.sql

# After
volumeMounts:
  - mountPath: /docker-entrypoint-initdb.d/init.sql
```

After editing, delete the Postgres pod so it reinitializes with the correct database name, then redeploy:
```bash
kubectl delete pod -l io.kompose.service=postgres
kubectl apply -k k8s/
kubectl delete pod -l io.kompose.service=via-tabloid-spring-boot  # force restart to clear backoff
```
